This guide describes a production controller-managed deployment. The controller runs in Kubernetes, PostgreSQL stores fleet state, your identity provider authorizes enrollment, and an MDM installs and configures the daemon on each endpoint.

The examples use these placeholders:

| Placeholder | Example |
| --- | --- |
| Controller hostname | `agentdesktop.example.com` |
| Inference gateway | `https://gateway.example.com` |
| OIDC issuer | `https://login.example.com` |
| OIDC client ID | `agentdesktop` |
| OIDC redirect URI | `http://127.0.0.1:51327/callback` |
| Kubernetes namespace | `agentdesktop` |

Replace every example value before deployment.

## Current production boundaries

Review these constraints before choosing agentdesktop for a production fleet:

- Enrollment is interactive. Each user must complete an OIDC browser flow; there is no MDM enrollment token or other zero-touch enrollment mode.
- A pending enrollment expires after 10 minutes. The daemon currently has to be restarted to begin another attempt after an expired or failed enrollment.
- Device-certificate renewal is checked when the daemon opens a controller stream, not by an independent renewal timer. Monitor certificate age and test recovery before relying on unattended renewal.
- The released Helm chart defaults to one controller replica. A highly available controller topology is not currently documented or validated.
- `existingConfigSecret` mounts only `controller.yaml`. If the controller also distributes a separate `daemon.yaml`, the chart needs the small overlay described below.
- The GCP template uses one PostgreSQL process, following kagent's bundled-database model. Regional persistent storage and backups improve recovery, but there is no automatic database failover.
- The release workflow signs controller images and provides endpoint installers. The OCI Helm chart has no signature or provenance step, so review and mirror the pinned chart and verify release checksums and installer signatures before deployment.
- The repository provides macOS and Windows machine installers. Linux binaries are released, but a production Linux package and service unit are not yet included.

Run a small pilot before broad deployment. In particular, verify every developer-tool version and every system-managed file path used in your environment.

## Production architecture

{{< production-architecture >}}

| Component | Responsibility |
| --- | --- |
| Identity provider | Authenticates the device user during enrollment. |
| Controller fleet API | Enrolls devices, issues device certificates, distributes desired configuration, and receives heartbeats and selected telemetry. |
| Controller management UI | Provides fleet inventory and configuration status through a loopback-only listener. |
| PostgreSQL | Stores controller state. |
| Inference gateway | Receives model traffic directly from supported developer tools. |
| Device daemon | Discovers tools, reconciles their managed configuration, and requests short-lived gateway credentials. |
| MDM | Installs the daemon and service, then writes its bootstrap configuration and any private trust roots. |

The fleet API uses TLS for server authentication. After enrollment, devices also present a controller-issued client certificate. Each daemon generates its device private key locally; only a certificate signing request is sent to the controller.

Developer-tool traffic does not pass through the controller. Claude Code, Claude Desktop, Codex, and OpenCode connect directly to the configured inference gateway. The controller only issues a short-lived gateway JWT when `controllerJwt` authentication is enabled.

Keep the two configuration layers separate:

1. MDM writes a small, stable bootstrap file containing only the controller address, heartbeat interval, and optional private CA path.
2. The controller distributes tool settings, gateway configuration, and telemetry policy as versioned daemon configuration.

## Prerequisites

Before deployment, prepare:

- A Kubernetes cluster and a PostgreSQL database reachable from it. The GCP deployment templates can create both in GKE.
- A public DNS name for the fleet API, such as `agentdesktop.example.com`.
- An HTTPS OpenID Connect issuer and a public native client registration.
- A server certificate valid for the fleet API DNS name.
- A dedicated private CA for issuing device client certificates.
- An endpoint-management system capable of installing packages, writing root-owned files, and managing a background service.
- Optionally, an inference gateway and an RSA signing key for controller-issued gateway JWTs.

Do not use the development certificates generated by the repository examples. Keep the controller TLS private key, device CA private key, database credentials, and optional gateway signing key in your production secret manager.

## 1. Configure the OIDC client

Create a **public native application** in the identity provider. The daemon does not send a client secret.

Configure the client with:

- Authorization Code flow.
- PKCE with the `S256` challenge method.
- Exact redirect URI `http://127.0.0.1:51327/callback`.
- Scopes `openid`, `profile`, `email`, and `offline_access`.
- ID tokens and refresh tokens enabled.
- A UserInfo endpoint that accepts the issued access token.

The controller requires the discovery document's `issuer` value to exactly match `oidc.issuer`. Avoid a trailing-slash mismatch. Apply the organization's MFA and device-access policy to this client, and limit access to users permitted to enroll endpoints.

Network requirements are:

- The controller must reach the issuer's discovery document, JWKS, and UserInfo endpoints.
- The machine daemon must reach the controller and the OIDC token endpoint from its root or `SYSTEM` service context, including through any required service proxy.
- The user's browser must reach the authorization endpoint and return to the loopback callback.
- Loopback TCP port `51327` must be available while the user completes enrollment.

The controller loads the identity provider's JWKS when it starts. Restart the controller after an IdP signing-key rotation if the new key is not already in that loaded set.

### Microsoft Entra ID

For a single-tenant Microsoft Entra deployment:

1. Open the [Microsoft Entra admin center](https://entra.microsoft.com), then go to **Entra ID > App registrations > New registration**.
2. Name the app `Agentdesktop enrollment`, choose **Accounts in this organizational directory only**, leave the redirect URI empty, and select **Register**.
3. Record the **Application (client) ID** and **Directory (tenant) ID**. Do not create a client secret.
4. Open **Manifest** and update the existing Microsoft Graph fields:

```json
"isFallbackPublicClient": true,
"publicClient": {
  "redirectUris": [
    "http://127.0.0.1:51327/callback"
  ]
}
```

Do not add the legacy Azure AD Graph fields `allowPublicClient` or `replyUrlsWithType`; the current manifest editor rejects them. Leave `web.implicitGrantSettings` disabled because Agentdesktop uses authorization code flow with PKCE, not implicit flow.

Limit who may enroll under **Enterprise applications > Agentdesktop enrollment > Properties** by enabling **Assignment required**. Assigning individual pilot users is valid. Group-based enterprise-application assignment can depend on tenant licensing, but this identity assignment is separate from Intune software targeting.

Use the exact canonical issuer returned by discovery. Entra may accept the tenant domain in the request but return the tenant GUID in `issuer`:

```sh
curl --fail --silent --show-error \
  "https://login.microsoftonline.com/TENANT_ID_OR_DOMAIN/v2.0/.well-known/openid-configuration" |
  jq -r .issuer
```

Set `OIDC_ISSUER` to that output without changing it and set `OIDC_CLIENT_ID` to the Application (client) ID.

## 2. Prepare certificates and signing keys

Agentdesktop uses three independent key purposes. Do not reuse keys between them.

### Fleet API server certificate

Obtain a server certificate whose SAN contains the exact externally resolved controller hostname. Store the leaf certificate followed by any intermediate certificates in `controller.pem`, and its unencrypted PEM private key in `controller-key.pem`.

The controller terminates TLS itself because it must receive the endpoint's client certificate. Expose it through an L4 load balancer or TCP TLS passthrough. Do not terminate TLS at a normal HTTP ingress.

If the server certificate chains to a public or enterprise root already trusted by endpoints, omit `controller.caCertificatePath` from the MDM bootstrap. Otherwise, MDM must deploy the issuing CA as a protected PEM file and reference it explicitly.

Inspect the certificate before loading it:

```sh
openssl x509 -in controller.pem -noout \
  -subject -issuer -dates -ext subjectAltName -ext extendedKeyUsage
openssl pkey -in controller-key.pem -pubout -outform DER | openssl sha256
openssl x509 -in controller.pem -pubkey -noout |
  openssl pkey -pubin -outform DER | openssl sha256
```

The two SHA-256 values must match.

### Device certificate authority

Create a dedicated issuing CA for agentdesktop device identities. Provide its PEM certificate as `device-ca.pem` and matching unencrypted PEM key as `device-ca-key.pem`. The certificate must be a CA certificate with certificate-signing key usage.

The controller keeps this key online because it signs enrollment CSRs. Use a dedicated intermediate or otherwise tightly scoped CA, store the source material in a secret manager, restrict access to the Kubernetes Secret, and audit every read. Do not use the organization's general-purpose root CA.

The daemon generates its private key locally. The controller accepts only the verified public key from the CSR and assigns the device identity itself. Issued client certificates are valid for 30 days. Before opening each controller stream, the daemon reuses the local key to request renewal when the certificate has 24 hours or less remaining. This is an opportunistic connection-time check, not a scheduled timer. If a certificate expires before renewal succeeds, sign out locally and enroll again.

The current controller has one active device issuer and no staged CA-rotation workflow. Treat replacement of this CA as a coordinated re-enrollment event and test it on a pilot group first.

### Gateway JWT signing key

This key is needed only when the controller issues inference-gateway credentials. Generate or provision an RSA private key in PKCS#8 or PKCS#1 PEM format as `gateway-jwt-key.pem`. The controller signs RS256 JWTs and publishes the public key at:

```text
https://agentdesktop.example.com/.well-known/jwks.json
```

The default token lifetime is five minutes. The published JWKS contains one active key and is cacheable for five minutes. The controller provides no old-and-new key overlap, so direct signing-key rotation cannot be guaranteed zero-downtime. Either configure an overlapping verifier set with gateway-specific controls or schedule a brief interruption while old tokens expire and the gateway refreshes JWKS.

### Create the Kubernetes TLS Secret

Prefer an external-secret controller that maps your secret manager's values to the required keys. For an initial controlled deployment, create the Secret from protected local files:

```sh
kubectl create namespace agentdesktop

kubectl -n agentdesktop create secret generic agentdesktop-controller-tls \
  --from-file=controller.pem=/secure/path/controller.pem \
  --from-file=controller-key.pem=/secure/path/controller-key.pem \
  --from-file=device-ca.pem=/secure/path/device-ca.pem \
  --from-file=device-ca-key.pem=/secure/path/device-ca-key.pem \
  --from-file=gateway-jwt-key.pem=/secure/path/gateway-jwt-key.pem
```

Omit the gateway key when gateway JWT issuance is disabled. Delete protected local copies according to your key-handling policy after the secret manager has accepted them.

## 3. Prepare PostgreSQL

Create a dedicated database and role. The role must be able to run the controller's built-in SQL migrations and read and write all tables in that database. Use encrypted PostgreSQL transport, for example a URL ending in `sslmode=verify-full`, and verify the database hostname against its certificate.

The controller opens a pool of up to 10 connections per process. Include that in connection-limit planning. Configure automated backups, restore testing, retention, and monitoring before enrollment begins.

Keep the complete database URL in the controller configuration Secret. Do not pass credentials in Helm values or place the URL in the chart-generated ConfigMap.

For GCP, use the [production deployment templates](https://github.com/agentdesktop-dev/website/tree/main/deploy/gcp). Their PostgreSQL chart follows kagent's direct `Deployment`, PVC, `PGDATA`, probe, security-context, and `pgvector/pgvector:pg18-trixie` pattern. It adds generated credentials, verified TLS, a retained regional persistent disk, NetworkPolicy, and daily `pg_dump` backups to a protected GCS bucket.

This remains a single database process with `Recreate` upgrades. Expect an outage while Kubernetes restarts the Pod or reattaches its disk. Use managed or operator-managed PostgreSQL instead when the required recovery-time objective needs automatic database failover.

## 4. Create controller and fleet configuration

Create a local `controller.yaml` for insertion into your secret manager:

```yaml
fleetListen: 0.0.0.0:8443
adminListen: 127.0.0.1:8080
databaseUrl: postgresql://agentdesktop:REDACTED@postgres.example.com:5432/agentdesktop?sslmode=verify-full
tls: /etc/agentdesktop/tls
allowInsecureDev: false

oidc:
  issuer: https://login.example.com
  clientId: agentdesktop
  redirectUri: http://127.0.0.1:51327/callback

gatewayJwt:
  privateKey: /etc/agentdesktop/tls/gateway-jwt-key.pem
  issuer: agentdesktop-controller
  keyId: agentdesktop-2026-01
  lifetime: 5m

daemonConfig:
  path: /etc/agentdesktop/config/daemon.yaml
  revision: 1
```

Omit `gatewayJwt` if it is not used. `adminListen` must remain loopback; the controller rejects a non-loopback address.

Next create `daemon.yaml`, the policy sent to enrolled endpoints:

```yaml
inferenceGateway:
  url: https://gateway.example.com
  authentication:
    type: controllerJwt
    audience: agentgateway
    allowedClientIds:
    - claude-code
    - claude-desktop
    - codex
    - opencode

telemetry:
  events:
  - session.new
  - tool.use

programs:
  claudeCode:
    permissions:
      defaultMode: plan
    companyAnnouncements:
    - Managed by your organization

  claudeDesktop:
    isLocalDevMcpEnabled: false

  codex:
    managedConfig:
      model_reasoning_effort: high

  openCode:
    model: company-model
    models:
      company-model:
        name: Company model
```

Only list clients you intend to authorize in `allowedClientIds`. `tool.use` reports tool metadata. `tool.use.input` additionally sends tool arguments and can contain prompts, source code, paths, or secrets; complete a privacy and security review before enabling it.

Validate and preview this controller-distributed policy on a disposable representative endpoint before uploading it:

```sh
sudo agentdesktop daemon --config ./daemon.yaml --dry-run
```

The command does not write files. A pre-existing managed file that agentdesktop does not own is reported as a conflict.

The controller UI's configuration builder generates YAML but does not save it. The watched `daemon.yaml` file remains the source of truth. Invalid replacements are rejected and the controller retains the last valid configuration.

### Managed client behavior

When a tool is present in `programs`, the daemon reconciles its system-managed configuration. Gateway-generated settings take precedence over overlapping pass-through settings.

| Client | Generated gateway behavior |
| --- | --- |
| Claude Code | Sets `ANTHROPIC_BASE_URL` and installs an `apiKeyHelper`. |
| Claude Desktop | Selects the gateway inference provider and installs a credential-helper script. |
| Codex | Adds an `agentdesktop` Responses API model provider and credential command. |
| OpenCode | Adds an `agentdesktop` provider, selected model, and credential plugin. |

System-mode defaults include:

| Managed artifact | Default path |
| --- | --- |
| Claude Code on macOS | `/Library/Application Support/ClaudeCode/managed-settings.d/50-agentdesktop.json` |
| Claude Code on Windows | `%ProgramFiles%\ClaudeCode\managed-settings.d\50-agentdesktop.json` |
| Claude Code on Linux | `/etc/claude-code/managed-settings.d/50-agentdesktop.json` |
| Claude Desktop settings | `/etc/claude-desktop/managed-settings.json` |
| Claude Desktop credential helper | `/etc/claude-desktop/agentdesktop-credential-helper` |
| Codex | `/etc/codex/managed_config.toml` |
| OpenCode settings | `/etc/opencode/opencode.jsonc` |
| OpenCode credential plugin | `/etc/opencode/plugins/agentdesktop.js` |

Agentdesktop marks files it owns and refuses to replace a conflicting file it did not create. Inventory existing management profiles and files before the pilot.

The current Windows service also receives the Unix-style `/etc` defaults for Claude Desktop, Codex, and OpenCode, and the MSI does not override them. Treat Windows managed paths as a production integration point. If the installed client expects another organization-managed location, customize the service arguments with `--claude-desktop-managed-settings`, `--claude-desktop-credential-helper`, `--codex-managed-config`, `--open-code-managed-config`, and `--open-code-plugin`, then test the resulting installer.

## 5. Install the controller

On GCP, first run the [local Kind smoke test](https://github.com/agentdesktop-dev/website/tree/main/deploy/kind), then follow the [infrastructure, image-build, and installation workflow](https://github.com/agentdesktop-dev/website/tree/main/deploy/gcp). It asks for the controller hostname before provisioning, prints the A and optional CNAME records for your existing DNS provider, waits for GKE, builds and pushes an AMD64/ARM64 controller image to a private Artifact Registry, validates OIDC discovery and certificates, installs PostgreSQL, and applies the controller chart overlay described below. It does not require a Cloud DNS zone. Cloudflare records must use **DNS only** because its normal proxy terminates the end-to-end TLS and client-certificate path.

### Account for the chart's policy-file mount

The current chart's `existingConfigSecret` branch selects only `controller.yaml`. A production configuration that also references `/etc/agentdesktop/config/daemon.yaml` will therefore fail unless the chart is extended.

Maintain a small chart overlay that mounts every key from the existing config Secret. In `templates/deployment.yaml`, the existing-secret volume should be equivalent to:

```yaml
- name: config
  secret:
    secretName: agentdesktop-controller-config
```

In other words, remove the `items` selection that projects only `controller.yaml`, or add a separate daemon-policy Secret volume. Keep this overlay in version control and rebase it when upgrading the chart.

Create the configuration Secret with both files:

```sh
kubectl -n agentdesktop create secret generic agentdesktop-controller-config \
  --from-file=controller.yaml \
  --from-file=daemon.yaml \
  --dry-run=client --output=yaml | kubectl apply -f -
```

### Install a pinned chart version

Set `VERSION` to a reviewed release without a leading `v`. Pull the chart so you can apply the overlay:

```sh
export VERSION=0.1.0

helm pull \
  oci://ghcr.io/agentdesktop-dev/charts/agentdesktop-controller \
  --version "${VERSION}" \
  --untar --untardir ./vendor
```

Apply the overlay, then install:

```sh
helm upgrade --install agentdesktop \
  ./vendor/agentdesktop-controller \
  --namespace agentdesktop \
  --set replicaCount=1 \
  --set existingConfigSecret=agentdesktop-controller-config \
  --set tlsSecretName=agentdesktop-controller-tls \
  --set service.type=LoadBalancer \
  --set service.port=443
```

The published controller image tag is `v${VERSION}`. The packaged chart uses that version by default. Pin the version in deployment automation and verify the signed image according to your software-supply-chain policy. The chart itself is not signed; review it and mirror the approved artifact into a trusted registry.

Point `agentdesktop.example.com` at the load balancer. The external path must preserve TLS and HTTP/2 end to end. Configure a TCP health check when the load balancer cannot probe gRPC without terminating TLS.

The chart does not currently define readiness probes, a PodDisruptionBudget, NetworkPolicy, or provider-specific Service annotations. Supply those through your platform overlay where required.

### Verify the controller

```sh
kubectl -n agentdesktop rollout status deployment/agentdesktop
kubectl -n agentdesktop logs deployment/agentdesktop

openssl s_client \
  -connect agentdesktop.example.com:443 \
  -servername agentdesktop.example.com \
  -verify_hostname agentdesktop.example.com \
  -verify_return_error \
  -alpn h2 </dev/null
```

Add `-CAfile /path/to/controller-ca.pem` when testing a private CA. Require a successful verification result and `ALPN protocol: h2` in the output.

Look for successful OIDC initialization, database migrations, device certificate issuance, and both listeners in the controller logs. If gateway JWT issuance is enabled, verify the public key:

```sh
curl --fail --silent \
  https://agentdesktop.example.com/.well-known/jwks.json
```

The management UI has no separate application authentication layer and remains loopback-only. Restrict Kubernetes port-forward access with RBAC:

```sh
kubectl -n agentdesktop port-forward deployment/agentdesktop 8080:8080
```

Then open [http://127.0.0.1:8080](http://127.0.0.1:8080).

If local port 8080 is occupied, forward a different local port, for example
`kubectl -n agentdesktop port-forward deployment/agentdesktop 18080:8080`, and
open [http://127.0.0.1:18080](http://127.0.0.1:18080). The public controller
hostname serves the fleet API on HTTPS 443, not this management UI; `/` may
correctly return `404`, and HTTP port 80 is not required.

## 6. Configure the inference gateway

Skip this section when no inference gateway is used.

Configure the gateway to:

- Accept traffic at the exact URL in `inferenceGateway.url`.
- Validate RS256 JWTs against the controller's public JWKS URL.
- Require issuer `agentdesktop-controller` and audience `agentgateway`, or the values selected in your configuration.
- Authorize the `client_id` claim for each supported developer tool.
- Use the `sub`, `act.sub`, email, and IdP claims only according to your reviewed authorization policy.
- Keep upstream provider credentials at the gateway; never distribute them to endpoints.

The JWT contains the OIDC subject in `sub`, the device ID in `act.sub`, the requesting tool in `client_id`, and selected verified IdP claims. Test expiry, clock skew, JWKS refresh, and key rotation before rollout.

## 7. Deploy through Microsoft Intune

Use **Microsoft Intune** as the MDM for this walkthrough. It manages both macOS and Windows, installs signed application packages, runs macOS scripts as root, delivers multi-file Windows packages in `.intunewin` format, and provides staged assignments and installation reporting.

Microsoft Entra ID and Intune have separate responsibilities:

- Entra authenticates users who enroll Agentdesktop.
- Intune enrolls and manages the Mac, installs the PKG, and runs the bootstrap script.
- Administrators use the browser-based [Microsoft Intune admin center](https://intune.microsoft.com); there is no Intune administrator application to download.
- A manually enrolled Mac uses the Microsoft Company Portal application.

Download the macOS PKG and Windows MSI for the same reviewed release as the controller. Verify their published checksums and platform signatures before uploading them to the MDM. Building or signing endpoint installers is not part of this deployment workflow.

Agentdesktop does not require Intune. See [MDM integrations](../mdm-integrations/) for Jamf Pro, Kandji, and Fleet deployment mappings.

Intune does not expose one cross-platform arbitrary-file payload. Use the platform-native delivery path instead:

| Platform | Application | Bootstrap files |
| --- | --- | --- |
| macOS | Required unmanaged macOS PKG app | Idempotent Intune root shell script |
| Windows | Required Windows app (Win32) | Files bundled with the MSI inside one `.intunewin` package |

The bootstrap and controller CA certificate are not secrets. Never put the device CA key, controller TLS key, gateway signing key, database URL, provider credentials, or any other secret in Intune scripts or app content.

### Prepare the Intune tenant

Confirm that the tenant has an Intune subscription, the pilot user has an Intune license, and the operator has the **Intune Administrator** role. Configure the Apple MDM push certificate under **Devices > Enrollment > Apple** before enrolling a Mac. Renew that certificate with the same Apple ID before it expires.

Prepare these Microsoft Entra device groups before uploading anything:

- `AgentDesktop-Pilot-macOS`
- `AgentDesktop-Pilot-Windows`
- One macOS and one Windows group for each later rollout ring

Assign applications and scripts to device groups rather than user groups so installation runs in the machine context and remains predictable on shared devices.

Intune application and script assignments target Microsoft Entra groups (or the broad **All users**/**All devices** virtual groups), not individual objects. Direct user assignment to the Agentdesktop Enterprise Application does not replace the Intune pilot device group. If the operator cannot create groups, a tenant administrator should create and maintain the pilot group; do not use **All devices** as a shortcut for an unsigned or untested package.

For a manually enrolled pilot Mac that is not yet in Apple Business Manager:

1. Download and install [Microsoft Company Portal for macOS](https://go.microsoft.com/fwlink/?linkid=853070).
2. Sign in with the licensed pilot user's Entra account and complete the management-profile prompts in macOS System Settings.
3. Confirm the Mac appears under **Devices > All devices** in Intune and add it to `AgentDesktop-Pilot-macOS`.
4. Confirm `/Library/Intune/Microsoft Intune Agent.app` is installed before expecting shell-script or unmanaged-PKG delivery.

For corporate Macs, configure [Apple Automated Device Enrollment](https://learn.microsoft.com/en-us/intune/device-enrollment/apple/setup-automated-macos):

1. Add the Apple MDM push certificate and Apple Business Manager enrollment-program token in Intune.
2. Go to **Devices > Device onboarding > Enrollment > macOS > Enrollment program tokens**.
3. Create a macOS enrollment policy with **User affinity**, **Setup Assistant with modern authentication**, **Await final configuration**, and **Locked enrollment**.
4. Assign the Company Portal and the enrollment policy to the pilot devices.
5. Verify `/Library/Intune/Microsoft Intune Agent.app` is installed before expecting PKG or shell-script delivery.

For corporate Windows devices, enable [automatic MDM enrollment](https://learn.microsoft.com/en-us/intune/device-enrollment/windows/enable-automatic-mdm):

1. Confirm the tenant has Intune and Microsoft Entra ID P1 or P2 licensing.
2. Go to **Devices > Device onboarding > Enrollment > Windows > Automatic Enrollment**.
3. Set **MDM user scope** to the pilot users first, then expand it with the rollout.
4. Enroll organization-owned devices through Windows Autopilot or Microsoft Entra join.

The Intune Management Extension installs automatically when a Win32 app is assigned. Intune's app and script channels are asynchronous: force **Sync** from the device record or **Check status** in Company Portal during the pilot, but allow for normal agent check-in delays in rollout planning.

### Create the endpoint bootstrap

The endpoint bootstrap contains only the controller connection. Gateway and developer-tool policy still comes from the controller.

Use this file when the controller certificate chains to a root already trusted by the operating system:

```yaml
controller:
  address: https://agentdesktop.example.com
  heartbeatInterval: 30s
```

For a private controller CA, macOS uses:

```yaml
controller:
  address: https://agentdesktop.example.com
  caCertificatePath: /etc/agentdesktop/controller-ca.pem
  heartbeatInterval: 30s
```

Windows uses `C:/ProgramData/AgentDesktop/controller-ca.pem` for the private CA path. The controller address must use HTTPS.

### Deploy macOS through Intune

The Agent Desktop PKG installs:

- `/Applications/agentdesktop.app`.
- The `dev.agentdesktop.daemon` system LaunchDaemon.
- `/etc/agentdesktop/config.yaml` when it does not already exist.
- Private state under `/var/lib/agentdesktop`.

Upload the signed and notarized PKG using Microsoft's [unmanaged macOS PKG app](https://learn.microsoft.com/en-us/intune/app-management/deployment/add-unmanaged-pkg-macos) workflow:

Before upload, require all three local checks to pass:

```sh
pkgutil --check-signature AgentDesktop.pkg
spctl --assess --type install --verbose=4 AgentDesktop.pkg
xcrun stapler validate AgentDesktop.pkg
```

The package must report a trusted **Developer ID Installer** signature, Gatekeeper must accept it, and the notarization ticket must validate. Intune's unmanaged-PKG channel can technically accept an unsigned package, but that is not a production exception to macOS signing and notarization requirements.

1. Go to **Apps > All Apps > Create**.
2. Select **macOS app (PKG)** and upload the approved PKG. The file must be smaller than 8 GB and must install successfully with macOS `installer` before upload.
3. Set the minimum operating system to macOS 12 or later, matching Intune's shell-script requirement.
4. Under detection rules, retain only the installed application with bundle ID `dev.agentdesktop.tray` and the release's bundle version. Set **Ignore app version** to **No**.
5. Assign the app as **Required** to `AgentDesktop-Pilot-macOS`.

Intune's unmanaged macOS PKG type has no **Uninstall** assignment. Remove Agent Desktop with a dedicated offboarding script before retiring a Mac from Intune.

When using the GCP deployment templates, render the environment-specific script from the controller hostname and public CA instead of manually editing a PEM block:

```sh
source deploy/gcp/.env.production

./deploy/gcp/scripts/render-intune-bootstrap.sh \
  "${CONTROLLER_HOSTNAME}" \
  deploy/gcp/agentdesktop-pki/controller-ca.pem \
  deploy/gcp/generated/agentdesktop-bootstrap.sh
```

The renderer is committed; the generated output is ignored because it is deployment-specific. The controller CA is public trust material, not the device CA or any private key. Upload the generated `agentdesktop-bootstrap.sh` to Intune.

For another platform or a manual workflow, create `agentdesktop-bootstrap.sh` with the following contents. Replace the controller address and the complete PEM block. When using public trust, remove `caCertificatePath`, `CA_PATH`, and the second `write_managed_file` call.

```sh
#!/bin/sh
set -eu

CONFIG_DIR=/etc/agentdesktop
CONFIG_PATH="${CONFIG_DIR}/config.yaml"
CA_PATH="${CONFIG_DIR}/controller-ca.pem"
changed=0

write_managed_file() {
  target="$1"
  mode="$2"
  temporary=$(/usr/bin/mktemp "${target}.XXXXXX")
  /bin/cat > "${temporary}"

  if [ -f "${target}" ] && /usr/bin/cmp -s "${temporary}" "${target}"; then
    /bin/rm -f "${temporary}"
    /usr/sbin/chown root:wheel "${target}"
    /bin/chmod "${mode}" "${target}"
    return
  fi

  /usr/sbin/chown root:wheel "${temporary}"
  /bin/chmod "${mode}" "${temporary}"
  /bin/mv -f "${temporary}" "${target}"
  changed=1
}

/usr/bin/install -d -o root -g wheel -m 0755 "${CONFIG_DIR}"

write_managed_file "${CONFIG_PATH}" 0600 <<'YAML'
controller:
  address: https://agentdesktop.example.com
  caCertificatePath: /etc/agentdesktop/controller-ca.pem
  heartbeatInterval: 30s
YAML

write_managed_file "${CA_PATH}" 0644 <<'PEM'
-----BEGIN CERTIFICATE-----
REPLACE_WITH_THE_COMPLETE_CONTROLLER_CA_CERTIFICATE
-----END CERTIFICATE-----
PEM

if [ "${changed}" -eq 1 ] &&
  /bin/launchctl print system/dev.agentdesktop.daemon >/dev/null 2>&1; then
  /bin/launchctl kickstart -k system/dev.agentdesktop.daemon
fi

console_user=$(/usr/bin/stat -f '%Su' /dev/console)
case "${console_user}" in
  "" | root | loginwindow | _mbsetupuser) ;;
  *)
    if ! /usr/sbin/dseditgroup -o checkmember -m "${console_user}" \
      agentdesktop 2>/dev/null | /usr/bin/grep -q 'yes'; then
      /usr/sbin/dseditgroup -o edit -a "${console_user}" -t user agentdesktop
    fi
    ;;
esac
```

### Deploy Windows through Intune

Deliver the signed MSI, bootstrap, optional controller CA, and installation logic as one [Windows app (Win32)](https://learn.microsoft.com/en-us/intune/app-management/deployment/add-win32). Do not mix a line-of-business MSI assignment with Win32 packages during Windows Autopilot enrollment.

On a Windows packaging host, create this directory:

```text
C:\Intune\AgentDesktop\
  agentdesktop.msi
  config.yaml
  controller-ca.pem
  install.ps1
```

Omit `controller-ca.pem` when using public trust, and remove `caCertificatePath` from `config.yaml`. Save `config.yaml` as UTF-8 without a BOM.

Create `install.ps1`:

```powershell
$ErrorActionPreference = "Stop"
$releaseVersion = "0.1.0"
$msi = Join-Path $PSScriptRoot "agentdesktop.msi"
$configSource = Join-Path $PSScriptRoot "config.yaml"
$caSource = Join-Path $PSScriptRoot "controller-ca.pem"
$root = Join-Path $env:ProgramData "AgentDesktop"
$configDestination = Join-Path $root "config.yaml"
$caDestination = Join-Path $root "controller-ca.pem"
$stateKey = "HKLM:\SOFTWARE\AgentDesktop\Intune"

$signature = Get-AuthenticodeSignature $msi
if ($signature.Status -ne "Valid") {
  throw "Agent Desktop MSI signature is $($signature.Status)"
}

$process = Start-Process msiexec.exe -ArgumentList @(
  "/i", "`"$msi`"", "/qn", "/norestart"
) -Wait -PassThru
if ($process.ExitCode -notin @(0, 3010)) {
  throw "Agent Desktop MSI failed with exit code $($process.ExitCode)"
}

New-Item -ItemType Directory -Path $root -Force | Out-Null
Copy-Item $configSource $configDestination -Force
if (Test-Path $caSource) {
  Copy-Item $caSource $caDestination -Force
} elseif (Test-Path $caDestination) {
  Remove-Item $caDestination -Force
}

& icacls.exe $root /inheritance:r /grant:r `
  "*S-1-5-18:(OI)(CI)F" "*S-1-5-32-544:(OI)(CI)F" `
  /T /C | Out-Null
if ($LASTEXITCODE -ne 0) {
  throw "Could not restrict $root"
}

Restart-Service AgentDesktop
$service = Get-Service AgentDesktop
$service.WaitForStatus("Running", [TimeSpan]::FromSeconds(30))

$executable = Join-Path $env:ProgramFiles "Agent Desktop\agentdesktop.exe"
& $executable status | Out-Null
if ($LASTEXITCODE -ne 0) {
  throw "Agent Desktop service is not reachable"
}

New-Item -Path $stateKey -Force | Out-Null
New-ItemProperty -Path $stateKey -Name ReleaseVersion `
  -Value $releaseVersion -PropertyType String -Force | Out-Null
New-ItemProperty -Path $stateKey -Name ConfigSha256 `
  -Value (Get-FileHash $configDestination -Algorithm SHA256).Hash `
  -PropertyType String -Force | Out-Null
$caHash = if (Test-Path $caDestination) {
  (Get-FileHash $caDestination -Algorithm SHA256).Hash
} else {
  ""
}
New-ItemProperty -Path $stateKey -Name CaSha256 `
  -Value $caHash -PropertyType String -Force | Out-Null
```

Update `$releaseVersion` for every release. The script validates the MSI signature, installs silently as `SYSTEM`, writes the bootstrap files, restricts their ACL, restarts the service, verifies the local API, and records expected file hashes for detection.

Download the latest [Microsoft Win32 Content Prep Tool](https://github.com/microsoft/Microsoft-Win32-Content-Prep-Tool) outside the source directory, then package all four files:

```powershell
IntuneWinAppUtil.exe `
  -c C:\Intune\AgentDesktop `
  -s install.ps1 `
  -o C:\Intune\Output `
  -q
```

Create `detect.ps1` separately and save it as UTF-8 with a BOM:

```powershell
$expectedVersion = "0.1.0"

try {
  $root = Join-Path $env:ProgramData "AgentDesktop"
  $state = Get-ItemProperty `
    "HKLM:\SOFTWARE\AgentDesktop\Intune" -ErrorAction Stop
  $config = Join-Path $root "config.yaml"
  $ca = Join-Path $root "controller-ca.pem"
  $executable = Join-Path $env:ProgramFiles "Agent Desktop\agentdesktop.exe"
  $service = Get-Service AgentDesktop -ErrorAction Stop

  if (-not (Test-Path $executable) -or
      -not (Test-Path $config) -or
      $state.ReleaseVersion -ne $expectedVersion -or
      $service.Status -ne "Running" -or
      (Get-FileHash $config -Algorithm SHA256).Hash -ne $state.ConfigSha256) {
    exit 1
  }
  if ($state.CaSha256 -and
      (-not (Test-Path $ca) -or
       (Get-FileHash $ca -Algorithm SHA256).Hash -ne $state.CaSha256)) {
    exit 1
  }

  Write-Output "Agent Desktop $($state.ReleaseVersion) is installed"
  exit 0
} catch {
  exit 1
}
```

Set `$expectedVersion` to the same value as `$releaseVersion` in `install.ps1` whenever a new app version is created.

Add the package to Intune:

1. Go to **Apps > All Apps > Create > Windows app (Win32)** and upload `install.intunewin`.
2. Set the install command to `%SystemRoot%\Sysnative\WindowsPowerShell\v1.0\powershell.exe -NoProfile -NonInteractive -ExecutionPolicy Bypass -File .\install.ps1`.
3. Set the uninstall command to `msiexec.exe /x ".\agentdesktop.msi" /qn /norestart`.
4. Set **Install behavior** to **System** and **Device restart behavior** to **No specific action**.
5. Select the package's matching x64 or ARM64 architecture and your supported minimum Windows version.
6. Choose a custom detection script, upload `detect.ps1`, set **Run script as 32-bit process on 64-bit clients** to **No**, and configure signature enforcement according to your PowerShell policy.
7. Assign the app as **Required** to `AgentDesktop-Pilot-Windows`.

Build separate Win32 apps for x64 and ARM64. For an upgrade, create a new versioned app and supersede the old one with **Uninstall previous version** set to **No**, allowing the MSI's stable upgrade code to perform the upgrade. An Intune **Uninstall** assignment removes the MSI payload but is not complete device offboarding; follow the cleanup procedure below.

### Enrollment timing

The installer starts the machine daemon immediately, but an enrollment attempt begins only when the bootstrap contains a controller. On macOS, the PKG and idempotent script can arrive in either order. On Windows, `install.ps1` installs the MSI, writes the files, and restarts the service as one reported operation.

Once the configured daemon starts, it immediately creates a 10-minute enrollment attempt. Wait for both macOS assignments, or the Windows Win32 app, to report success before notifying the user. The desktop app's **Enroll device** button opens the authorization URL already held by the daemon; it does not create a fresh attempt. If the user did not complete sign-in in that window, use a one-time Intune root/system script to restart the service immediately before they open Agent Desktop:

```sh
# macOS
launchctl kickstart -k system/dev.agentdesktop.daemon
```

```powershell
# Windows
Restart-Service AgentDesktop
```

The user then opens Agent Desktop, selects **Enroll device**, and completes the OIDC flow in the default browser. The desktop UI polls the daemon until enrollment completes.

Enrollment stores device metadata under the machine state directory. The private device key and OAuth tokens use the operating system credential store on macOS and Windows. On Linux they are owner-only files under the state directory.

## 8. Validate a pilot endpoint

Perform all of these checks before increasing the MDM assignment:

1. Confirm the service survives a reboot and the local status command prints `ok`.
2. Complete enrollment and verify the correct user, hostname, OS, architecture, and agent version in the controller UI.
3. Confirm the configuration state becomes **Applied** at the intended revision.
4. Restart the daemon after installing or removing developer tools, then run `agentdesktop discover` with the installed binary. Discovery is a startup snapshot, not a live rescan.
5. Inspect the generated managed files and verify that unrelated user settings remain intact.
6. Start each managed tool and confirm its model requests reach the inference gateway.
7. Verify the gateway accepts a short-lived controller JWT and rejects an expired token, wrong audience, and unapproved client ID.
8. Confirm only the selected telemetry events appear. Inspect payloads before enabling telemetry beyond the pilot.
9. Disconnect the controller temporarily and confirm the daemon continues using its cached last accepted configuration.
10. Test upgrade, rollback, unenrollment, and complete offboarding on both CPU architectures in use.

`agentdesktop config` prints the local MDM bootstrap, not the controller-distributed effective policy. Use the desktop UI's advanced configuration view, the controller UI, or the protected `remote-config.yaml` in the daemon state directory when diagnosing remote policy.

## 9. Roll out and operate

Use deployment rings such as platform engineering, volunteer developers, one business unit, and then the general fleet. Gate each ring on enrollment success, configuration failures, gateway authentication failures, and support volume.

For each policy rollout:

1. Validate `daemon.yaml` against the schema in the source repository.
2. Run `agentdesktop daemon --config ./daemon.yaml --dry-run` and review the generated changes on representative endpoints.
3. Increment `daemonConfig.revision` in `controller.yaml`.
4. Scale the single-replica controller to zero and wait for its Pod to stop.
5. Update the combined Kubernetes configuration Secret.
6. Scale the controller back to one and wait for rollout completion.
7. Watch **Applied** and **Failed** counts before expanding the ring.

```sh
kubectl -n agentdesktop scale deployment/agentdesktop --replicas=0
kubectl -n agentdesktop wait --for=delete pod \
  -l app.kubernetes.io/instance=agentdesktop --timeout=120s

kubectl -n agentdesktop create secret generic agentdesktop-controller-config \
  --from-file=controller.yaml \
  --from-file=daemon.yaml \
  --dry-run=client --output=yaml | kubectl apply -f -

kubectl -n agentdesktop scale deployment/agentdesktop --replicas=1
kubectl -n agentdesktop rollout status deployment/agentdesktop
```

This brief stop avoids publishing new policy with the old revision: a running controller watches `daemon.yaml`, but its revision is fixed when the process starts. A live invalid policy replacement retains the last valid policy; an invalid file present during startup prevents the controller from starting, which is why the dry run comes first. Controller startup configuration, certificates, OIDC JWKS, and signing keys are also loaded at process start.

### Backup and recovery

Back up PostgreSQL and the source values in the secret manager. A replacement controller needs the same database, server identity, device CA, and gateway signing key to preserve normal connectivity. Test restoration into an isolated environment.

The GCP deployment runs a daily PostgreSQL 18 custom-format dump and uploads it, with a SHA-256 file, to the retention-protected bucket using Workload Identity. Run `./deploy/gcp/deploy.sh backup` before a risky change. A backup is useful only after a tested restore: scale the controller to zero, suspend scheduled backups, restore with the matching PostgreSQL major version, restart the controller, and run deployment verification before admitting endpoints.

Do not restore endpoint state to another machine. Device private keys are machine identities and must be generated locally through a new enrollment.

### Rotation

- **Server certificate:** update `controller.pem` and `controller-key.pem`, then restart the controller before expiry.
- **OIDC signing keys:** restart the controller after the IdP publishes a key not present when the controller started.
- **Gateway JWT key:** the current JWKS exposes one key with five-minute caching and no overlap. Use gateway-specific overlapping verifier controls or schedule an authentication interruption while tokens and caches expire, then change `keyId`, update the key, and restart the controller.
- **Device CA:** plan a fleet re-enrollment and local sign-out. The current controller does not provide overlapping issuer rotation.

### Device removal and offboarding

Deleting a device in the management UI makes future authenticated RPCs and reconnections fail, but it does not synchronously close an established stream or revoke a gateway JWT already issued for up to its configured lifetime. An otherwise authorized user can also enroll again. Permanent offboarding therefore requires removing IdP access, withdrawing MDM policy, and stopping or remediating the endpoint.

The Windows MSI preserves machine configuration, and the macOS PKG has no uninstall command. Removing the state directory alone does not delete private keys and OAuth tokens from macOS Keychain or Windows Credential Manager. Removing the installed application also does not remove agentdesktop-owned tool settings, helper scripts, or plugins.

For complete offboarding:

1. Remove the user's IdP entitlement and withdraw the endpoint's MDM assignment.
2. While the daemon and its identity metadata still exist, use **Sign out** in Agent Desktop. This deletes the native credential-store entries and local identity.
3. Stop the service. Apply an empty standalone configuration once with `agentdesktop daemon --config ./empty.yaml --once` so the reconciler removes files it owns.
4. Uninstall the service and application, then remove the machine configuration, private CA copy, and state directory with a privileged MDM action.
5. Delete the device in the controller UI and allow the maximum gateway JWT lifetime to elapse.
6. Confirm the gateway no longer accepts credentials for that device.

On macOS, run step 3 through MDM as root:

```sh
launchctl bootout system/dev.agentdesktop.daemon
printf '{}\n' > /private/tmp/agentdesktop-empty.yaml
"/Applications/agentdesktop.app/Contents/MacOS/agentdesktop" daemon \
  --config /private/tmp/agentdesktop-empty.yaml --once
rm -f /private/tmp/agentdesktop-empty.yaml
```

On Windows, run it through MDM or an elevated PowerShell session:

```powershell
Stop-Service AgentDesktop
$empty = Join-Path $env:TEMP "agentdesktop-empty.yaml"
[IO.File]::WriteAllText($empty, "{}`n", [Text.UTF8Encoding]::new($false))
& "$env:ProgramFiles\Agent Desktop\agentdesktop.exe" daemon `
  --config $empty --once
Remove-Item $empty -Force
```

If local sign-out cannot run, the current product has no privileged purge command for orphaned Keychain or Credential Manager entries; handle those through platform credential-store remediation or device reimaging.

## Troubleshooting

| Symptom | Check |
| --- | --- |
| TLS hostname or trust failure | Certificate SAN, full intermediate chain, endpoint clock, DNS, and `caCertificatePath`. |
| Enrollment RPC fails behind a load balancer | Confirm L4 TLS passthrough and HTTP/2; the controller must terminate TLS and see the client certificate. |
| OIDC initialization fails | Exact issuer match, HTTPS discovery, JWKS and UserInfo reachability, and public-client configuration. |
| Enrollment page expired or UI remains unavailable | Restart the machine daemon to create a new 10-minute enrollment attempt. |
| Device certificate expired before renewal | Use Agent Desktop to sign out locally, restart the daemon, and enroll again; do not only delete the state directory. |
| Desktop UI cannot reach the macOS daemon | Check the `agentdesktop` group, socket permissions, and whether the user signed in again after group assignment. |
| Controller cannot find `daemon.yaml` | Apply the existing-config Secret chart overlay and confirm both files are mounted under `/etc/agentdesktop/config`. |
| Managed file conflict | Remove or migrate the pre-existing system-managed file; agentdesktop will not overwrite a file it does not own. |
| Gateway returns 401 | Compare JWT `iss`, `aud`, `client_id`, expiry, gateway clock, and the configured JWKS URL. |
| Configuration stays failed | Read the per-device error in the controller UI and verify paths, permissions, and tool-specific setting types. |
